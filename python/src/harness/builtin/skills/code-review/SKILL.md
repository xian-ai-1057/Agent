# 審查程式碼

目標是找出**真正會出問題**的地方，而不是列出所有可以改的細節。每一個
發現都要說得出「在什麼情況下會出錯、錯成什麼樣子」。

## 步驟

1. **確定審查範圍。** 使用者沒指定時，依序嘗試：
   - `git diff --staged` 與 `git diff`（尚未 commit 的變更）
   - `git diff <預設分支>...HEAD`（目前分支相對於主線的變更；預設分支
     可以用 `git symbolic-ref refs/remotes/origin/HEAD` 或看 `git branch -a`）
   - 使用者指定的檔案或資料夾
   先用 `git diff --stat` 掌握規模；範圍很大時告訴使用者你會先看哪些部分。
2. **讀懂意圖。** 看 commit 訊息（`git log --oneline -n 20`）、相關的
   issue 或 PR 說明，以及專案的 README、AGENTS.md、CONTRIBUTING 等規範
   文件。審查是對照「它想做什麼」來看「它做對了沒有」。
3. **讀完整的上下文。** 不要只看 diff。用 `read_file` 讀變更所在的整個
   函式與呼叫它的地方，用 `search_files` 找同一個函式或設定的其他用法，
   確認改動沒有破壞別處。
4. **逐項檢查**，依 `checklist.md` 的順序，重要的先看。
5. **驗證懷疑。** 對不確定的問題，盡量用證據確認：找到實際觸發的程式
   路徑、跑相關測試（例如 `npm test`、`pytest -q <檔案>`）、或寫一個最小
   的重現。無法確認的標成「待確認」，不要當成事實。
6. **回報**（格式見下方）。不要修改任何檔案，除非使用者要求。

## 回報格式

依嚴重程度由高到低排列，每一項：

```
[嚴重] src/orders.py:42 — 退款金額沒有檢查上限
  情境：refund_amount 大於原訂單金額時會直接退款，使用者可以退出比付款
  更多的錢。
  建議：在 issue_refund 前比對 order.total。
```

嚴重程度：
- **嚴重**：資料錯誤、資料遺失、安全漏洞、正式環境會壞掉
- **重要**：特定情況下的錯誤行為、缺少錯誤處理、明顯的效能問題
- **建議**：可讀性、重複程式碼、命名、缺少測試

最後用一兩句話總結：整體品質、最需要先處理的是哪一項。沒有發現問題時
就直說沒有，並說明你檢查了哪些範圍，不要為了湊數而挑小毛病。
