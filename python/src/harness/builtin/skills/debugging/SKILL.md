# 系統化除錯

除錯最常見的失敗是「還沒找到原因就開始改程式」。照下面的順序做，每一
步都要有證據，不要憑感覺跳到結論。開始前用 `update_plan` 列出步驟，讓
使用者看得到進度。

## 1. 重現

- 問清楚（或從訊息裡找出）：做了什麼、預期什麼、實際發生什麼、完整的
  錯誤訊息與堆疊。
- 用 `run_command` 實際跑一次，親眼看到同樣的錯誤。重現不了就先回頭
  確認環境、輸入資料與版本，不要在重現之前修改程式。
- 盡量把重現縮成一個指令或一個最小的測試案例，之後每次修改都用它驗證。

## 2. 縮小範圍

- 從錯誤訊息與堆疊找到出錯的檔案與行號，用 `read_file` 讀完整的函式。
- 用 `search_files` 找相關的呼叫、設定與錯誤訊息的出處。
- 問題是最近才出現的話，用 `git log -n 20 --oneline` 與 `git diff` 看
  最近改了什麼；必要時用 `git bisect` 找出是哪個 commit 造成的。
- 對半切：註解掉一半的步驟、換一半的輸入，看問題還在不在。

## 3. 提出並驗證假設

- 一次只提出一個具體的假設，例如「`parse_date` 在輸入沒有時區時回傳
  naive datetime，和資料庫裡的 aware datetime 比較時出錯」。
- 用最便宜的方式驗證：加一行暫時的 print / log、在 REPL 裡跑一小段、
  寫一個針對性的測試。
- 假設被推翻就換下一個，並記下已經排除的可能。不要同時改好幾個地方。

## 4. 修正

- 修在根本原因上，而不是在出錯的地方加特例掩蓋症狀。
- 改動盡量小，只改和這個問題有關的地方（用 `edit_file`）。
- 加上一個能重現這個問題的測試；修正前它應該失敗，修正後通過。
- 移除除錯時加的暫時 print / log。

## 5. 確認

- 再跑一次第 1 步的重現，確認問題消失。
- 跑相關的測試套件，確認沒有弄壞別的東西。

## 回報

用幾句話說明：根本原因是什麼、怎麼找到的、改了哪些地方、怎麼驗證的。
如果最後沒有找到原因，誠實說明已經排除了哪些可能、下一步建議查什麼，
不要宣稱已經修好。
